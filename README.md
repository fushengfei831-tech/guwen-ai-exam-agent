# 古代文学考研 AI 助手 · 出题 / 判卷 / 讲评

> 一个面向中国古代文学考研场景的 AI 学习助手，以及围绕它做的**一次完整的量化评测与检索链路排查**。

---

## 一、项目简介

- **场景**：文学考研的出题判卷模式全流程依赖人工，评分标准模糊、反馈周期长；通用大模型在回答时易产生幻觉，编造出处、混淆朝代。
- **做法**：本地自托管 Dify，构建 276 道真题题库知识库 + Agent 编排，实现「出题 → 判卷 → 讲评」闭环，并用**量化评测**验证效果、定位问题。
- **我的角色**：独立完成（题库整理、知识库构建、工作流编排、评测集设计、实验执行与数据分析）。

---

## 四、核心结果：A/B 对照实验

**实验设计**：同一模型、同一提示词、同一批 30 道题，**唯一变量 = 是否挂载知识库**。

| 指标 | A 组（无知识库） | B 组（有知识库） | 差值 |
|---|---|---|---|
| **要点覆盖率** | **77.6%** | **97.2%** | **+19.6 个百分点** |
| 要点 100% 全覆盖题数 | 15 / 30 | **28 / 30** | +13 |
| 平均回答字数 | 537 字 | **284 字** | −253（更短更准） |
| 平均 prompt tokens | 39 | 898 | +859 |

**分时期增益**（增益集中在冷门/细节题）：

| 时期 | A 组 | B 组 | 差值 |
|---|---|---|---|
| 清代 | 50.0% | 100% | **+50.0** |
| 明代 | 54.2% | 100% | **+45.8** |
| 先秦 | 71.7% | 100% | +28.3 |
| 隋唐五代 | 75.3% | 100% | +24.7 |
| 魏晋南北朝 | 77.8% | 94.4% | +16.7 |
| 宋代 | 88.3% | 90.0% | +1.7 |
| 秦汉 / 辽金元 | 100% | 100% | 0 |

> **一个被数据推翻的预期**：原假设「冷门时期模型更差」，但实测秦汉、辽金元 A 组本来就是 100%。真实规律是：**模型的知识盲区按「具体知识点」分布，而非按「时期冷门度」分布**。

## 五、三个工程发现

### 发现 1：题库跨题型重复命题

**现象**：评测第 10 题「简述梅尧臣诗歌的艺术特点」出现**反例**——带知识库反而更差（覆盖率 100% → 50%）。

**根因**：题库中同一知识点收录了两道题：

| 题号 | 题型 | 答题要点 |
|---|---|---|
| 193 | 简答题 | 4 条（详细） |
| 230 | 论述题 | 3 条（简略） |

检索命中了**论述题**那条，把简略答案塞给了问简答题的模型。

**扩大排查**：审计全库 276 题，识别出 **55 组同知识点重复命题（涉及 88 题，占 32%），其中 38 组为跨题型**。

### 发现 2：Rerank 故障导致检索链路静默失败 ⭐

**现象**：知识库检索突然对**所有问题**返回 0 条片段，四种完全不同类型的问题全部为空。

**排查过程**（排除了 4 个可疑项）：

| 排查项 | 结论 |
|---|---|
| 元数据过滤 | 关掉过滤后仍为 0 条 → 排除 |
| 文档标签赋值 | 已正确赋值 → 排除 |
| 索引模式 | 已切换为高质量 → 排除 |
| 网络与密钥 | 容器内直连与走代理均返回 401（链路正常）→ 排除 |

**根因**：`https://api.siliconflow.cn/v1/rerank` 返回 **403 Forbidden**，导致重排序环节失败、**整条检索链路中断**。

**关键点**：**知识库的召回测试会弹出报错，但应用侧是静默失败的**——只表现为「模型突然什么都不知道了」，极难定位。

**修复**：关闭 Rerank → 检索恢复；配合语义检索，该题覆盖率由 50% **恢复至 100%**（检索分数：简答题 0.746 vs 论述题 0.745，仅差 0.001）。

> RAG 系统中辅助组件的故障，会以「检索为空」的形式表现出来。据此提出监控建议：**召回片段数为 0 时告警**，而不是等用户反馈回答变差。

---

### 发现 3：出题工具失效 → 出题链路修复 ⭐

**问题**：原出题链路依赖一个 LLM 工作流工具。实测记录（n=17）：

- 入参 `query` **不进入生成模型**，17 次调用与输入的朝代/作家**命中数 0**；
- 输出高度集中，仅 4 类稳定出现（魏晋南北朝＝陶渊明、宋＝苏轼、先秦＝《诗经》/《左传》、隋唐五代＝杜甫），**秦汉 / 辽金元 / 明 / 清 出现 0 次**；
- 单次出题最多触发 **12 次**工具调用，响应 **100–200 秒**。

**根因定位**：工作流结构为「用户输入(query) → 知识检索 → LLM」，但 LLM 节点提示词中的 `query` **未被正确引用**（手工输入而非从变量面板插入变量），模型收到的是字面量 `{{query}}`，于是每次都判定"超出范围"并退化为随机出题。

**修复**：在 LLM 节点提示词中通过变量面板正确插入 `query`，并把知识检索结果接入 LLM 上下文；重新发布工作流，并在 Agent 系统提示词中加入执行纪律（禁止 shell 探查、限定工具调用次数）。

**验证结果（8 个时期 × 2 次 = 16 次调用）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 朝代命中率 | 0 / 17 | **16 / 16 = 100%** |
| 稳定可出题的时期 | 4 / 8 | **8 / 8** |
| 响应时间 | 100–200 秒 | **平均 11.1 秒**（最快 7.9 / 最慢 16.8） |
| 答案泄露（输出参考答案） | 有风险 | **0 次** |
| `<think>` 推理泄露 | 有 | **0 次** |



## 六、方法说明与局限

**评测方法**
1. 评分标准使用题库原有的【答题要点】，不主观打分；
2. 判定采用 **LLM-as-judge**：逐条判断「是否覆盖该要点」，**措辞不同也算覆盖**；
3. **随机交换两份回答的呈现顺序**，消除位置偏差；
4. 另用字符二元组规则匹配法交叉验证，**逐点一致率 73.1%**。

**为什么不用纯程序匹配**：第一版用字符串匹配算出 38.6% → 85.0%，抽查发现**严重漏判**——模型把「根据《离魂记》改编」表述为「取材于唐传奇《离魂记》」，字面对不上但语义完全覆盖。**主观题评测必须用模型裁判，规则匹配会系统性低估。**

**局限（必须如实说明）**
1. 知识库中包含参考答案，因此本实验测量的是「**能否检索并完整复述标准内容**」，不等于模型的独立推理能力；
2. 样本 30 题，足以定位系统性问题，**不足以做统计显著结论**；
3. LLM-as-judge 存在裁判偏好，已通过随机化顺序缓解，并与规则法做逐点交叉验证。
